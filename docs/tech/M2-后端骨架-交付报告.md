## 二、技术决策与取舍

### 2.1 鉴权方式：无状态 HS256 JWT（**非** 表存 token）

| 取舍 | 理由 |
|---|---|
| ✅ 选 JWT | 横向扩容无需共享会话存储；载荷可带 email/userId，省一次 DB 查询；前端存 localStorage 即可 |
| ⚠️ 代价 | 主动吊销需黑名单——MVP 不做（无改密 / 踢下线 需求） |
| 密钥 | `PETIBI_JWT_SECRET` 环境变量；dev 默认 `petibi-dev-secret-change-me`，生产部署**必须**显式设置 |
| 过期 | 默认 30 天（`PETIBI_JWT_EXPIRES`），与浏览器 session 习惯一致 |

### 2.2 数据库：better-sqlite3 + 文件型

- 表结构与 `M3-对话链路契约.md` §4 字段**逐项**对齐：`users(email UNIQUE, nickname, mbti, subtype, created_at)` / `email_codes(email, code, expires_at)` / `chat_usage(user_id, date, count, UNIQUE(user_id,date))` / `chat_logs(id, user_id, question, answer, rag_entry_id, created_at)`
- 启用 `journal_mode=WAL` + `foreign_keys=ON`（chat_usage / chat_logs 通过 `users.id` ON DELETE CASCADE）
- 测试场景切 `":memory:"`，每个用例自带干净 DB
- 文件路径默认 `data/server.db`（与现有 data/ 同级；首次启动自动建父目录）

### 2.3 验证码：6 位数字，10 分钟过期，一次性消费

- 生成：`crypto.randomInt(0, 10**6)` 避免 `Math.random` 偏置
- 过期：精确到毫秒（`expires_at` 用 `INTEGER` 存毫秒时间戳）
- 一次性消费：verify 通过后立即 `DELETE` 该邮箱的全部码；过期路径同样清表
- **Latest wins**：同邮箱再次发码时先 DELETE 再 INSERT，避免旧码被新码覆盖后还能用

### 2.4 dev 模式验证码直返响应

- 响应体 `devCode` 字段（仅 `PETIBI_ENV=dev|test` 时返回；prod 强制 undefined）
- 同步打结构化日志：`Petibi [mail] dev code=123456 to=foo@bar.com expiresIn=600s`
- ProdMailer 为显式占位：未实现直接抛错，避免静默默认

### 2.5 写档校验：16 型 + 两档 subtype 白名单

- MBTI 走 `Set` 白名单（与计分引擎 `score.ts` 保持一致）
- subtype 限 `stable | sensitive`（与计分引擎 `FIRST_POLE.ES` 一致）
- 重复写档 → 409（编辑场景需要更复杂的产品语义，超出本工单范围）
- 昵称限长 32 字符，自动 trim

### 2.6 配额：每日 10 次，按用户维度计数（**R4 红线**）

- `chat_usage` 表 `UNIQUE(user_id, date)`，跨设备/重启不重置
- `INSERT ... ON CONFLICT DO UPDATE` 原子读+增；先 hasQuotaRemaining 再 incrementTodayUsage，避免超额写库
- 上限可配（`PETIBI_DAILY_QUOTA`，默认 10）
- 第 11 次真实工单实现 `/api/chat` 时，由路由调用 `hasQuotaRemaining` → 不通过即抛 `AppError.quotaExceeded()`（已实现，状态码 403 + 错误码 `QUOTA_EXCEEDED`）

### 3.2 错误路径

```bash
# 非法邮箱
$ curl -X POST http://127.0.0.1:18788/api/auth/email/code \
       -H 'Content-Type: application/json' -d '{"email":"not-an-email"}'
{"ok":false,"error":{"code":"INVALID_EMAIL","message":"邮箱格式不正确"}}   # 400

# 验证码错误（latest wins 后旧码立即失效）
$ curl -X POST http://127.0.0.1:18788/api/auth/email/verify \
       -H 'Content-Type: application/json' -d '{"email":"alice@petibi.app","code":"000000"}'
{"ok":false,"error":{"code":"INVALID_CODE","message":"验证码错误或已过期"}}   # 400

# 无 token 访问 /api/quota
$ curl http://127.0.0.1:18788/api/quota
{"ok":false,"error":{"code":"UNAUTHORIZED","message":"缺少 Bearer token"}}   # 401

# 写档：MBTI 非 16 型 → 400 INVALID_PROFILE
# 写档：subtype 非两档 → 400 INVALID_PROFILE
# 写档：昵称为空 / 超长 → 400 INVALID_PROFILE
# 写档：已写档再写 → 409 INVALID_PROFILE
# 未知路径 → 404 NOT_FOUND
```

### 3.3 错误码规范

| code | HTTP | 触发场景 |
|---|---|---|
| `INVALID_EMAIL` | 400 | 邮箱格式非法 / 缺失 |
| `CODE_FORMAT_INVALID` | 400 | 验证码非 6 位数字 |
| `INVALID_CODE` | 400 | 验证码错误 / 已过期 / 已消费 |
| `INVALID_PROFILE` | 400 / 409 | 写档参数非法 / 重复写档 |
| `UNAUTHORIZED` | 401 | 缺 Bearer token / token 无效 / token 过期 |
| `QUOTA_EXCEEDED` | 403 | 当日 10 次用完（R4） |
| `USER_NOT_FOUND` | 404 | 路由层兜底（理论上不会出现） |
| `NOT_FOUND` | 404 | 路径未匹配任何路由 |
| `NOT_IMPLEMENTED` | 501 | `/api/chat` 占位（待 M3 RAG 工单） |
| `INTERNAL` | 500 | 未捕获异常 |

所有错误统一响应形状：`{ ok: false, error: { code, message } }`；所有成功响应：`{ ok: true, ...data }`。

   - **配额检查**：`hasQuotaRemaining(db, userId, config.dailyQuota)`，不通过抛 `AppError.quotaExceeded()`

3. 把 chat 测试补到 `server/__tests__/chat-route.test.ts`（pre-existing 占位文件已有，待接管）

### 7.2 已知遗留

- **JWT 黑名单**：当前不支持主动吊销（无踢下线需求）。如未来要做"改密踢出"或"管理员强制下线"，需加 token_version 字段 + 中间件校验。
- **写档只允许一次**：写档后再次 POST /api/me/profile → 409。编辑场景需要在产品层确认语义后再加 PATCH。
- **rate limiting / 风控**：当前没有任何 IP/邮箱维度限流，发码接口可被脚本刷。生产部署建议前置 Nginx 限流或在路由内加简单计数。
- **/api/me/profile 字段顺序**：M3 接管对话时，DB 中 mbti/subtype 字段已经写入；对话工单需确认是否要在 prompt 工程里读取这两个字段。
- **pre-existing `server/src/`、`server/tests/`、`server/package.json`、`server/tsconfig.json`、`server/vitest.config.ts`**：本轮**未触碰**，是仓库里前一轮已存在的备用 scaffold（含 intent-filter / personas / refusals / rag / llm 等尚未启用的模块）。本轮交付的 `server/` 根目录下的文件与这些 pre-existing 文件**互不依赖、互不引用**，命名空间隔离。本轮 tsconfig / 根 vitest config 仅 include `server/__tests__/**` 与 `src/scoring/**`，不会扫到 `server/src/**`。建议下个工单整合两套 scaffold，决定去留。

### 7.3 与 R9 红线的兼容性

`scripts/check_comments.py` 把 `server/` 根 + `server/utils/` + `server/routes/` + `server/__tests__/` 下的所有 `.ts` 都纳入扫描（前 5 行必须含中文注释标记）。本轮新增 17 个文件**全部带中文文件头 + 关键函数中文行注释**。当前覆盖率 94/94。
