## 3. 设计取舍说明

### 3.1 测试框架选 vitest 而非 jest
- 项目已有 `vite@^5.4` 在 devDependencies 里（electron-vite 间接依赖），vitest 复用 vite 的 transformer（esbuild），比 jest + ts-jest 配置成本低
- electron-vite 项目对 vitest 兼容：vitest 1.6 用独立的 `vitest.config.ts`，不会触碰 `electron.vite.config.ts` 的主进程/渲染进程编译管线，因此无需改 electron-vite 配置
- vitest 默认会扫 `**/*.test.ts`，为避免误扫描 `src/App.tsx` `src/main.tsx`（注入 React 渲染入口），把 `include` 显式收紧到 `src/scoring/**/*.test.ts`
- 选 `environment: "node"`：纯函数无 DOM/jsdom 需求，且避免 happy-dom/jsdom 拉启动开销

### 3.2 极性判定抽到 `FIRST_POLE` 表
- §4 接口只定义 "EI/SN/TF/JP/ES" 五维和 "E/S/T/J/stable" 第一极字符串，但实际判定要按维度查第一极。把 "极性 → 第一极" 的映射抽成单一真理源（`types.ts` 的 `FIRST_POLE`），`scoreOne`、阈值判定都消费同一张表，避免不同分支对 "第一极是谁" 给出不一致答案
- ES 第一极字符串在表里就是 `"stable"`（与数据契约 §1 注 "避免与 EI 的 E 混淆" 一致），这一决策在 `FIRST_POLE 表自检` describe 块里单独断言锁死

### 3.3 平局（恰好 50）取第一极的实现位置
- 阈值判定只有一处（在 `score()` 末尾）：`percentages[dim] >= 50 ? firstPole : secondPole`
- 一处实现 + 一处事实 → 红线 R5 的 "确定性" 不是靠多分支统一，而是靠数学本身（不依赖随机/时间/IO）+ 代码单点裁定
- 测试用例 "所有题打 3 → 50% → 第一极" 在 5 维度同时验证这一规则（任何一个维度取错第二条就 fail）

### 3.4 浮点末位处理
- 聚合分数是整数求和、单题分量 0..4，所以默认不会引入浮点误差
- 但为防将来题库结构升级（如新增加权题型），`round2(n * 100) / 100` 做"归一化百分比保留两位小数"
- 第二条确定性测试用例专门构造 "非整数百分比"（EI01=1, EI02=2 → 37.5%），验证 `JSON.stringify(score(...))` 100 次逐字一致

### 3.5 方向归一：方向是"加给第一极的方向"
- §4 规则读法：第一极题（direction = FIRST_POLE[dim][0]）scoreOne = answer - 1；第二极题（反向题）scoreOne = 5 - answer
- 两种题"加给的都是第一极分"，最后百分比意义就是"第一极占比"。这样正向题与反向题在数学上对称，不必在聚合时再按维度分开统计
- 反向题的设计动机（数据契约 §1 注 "防默认赞同偏差"）在题库工单体现；引擎只负责算分，不管题的方向选择

### 3.6 输入校验放在聚合之前
- 缺题（`answers[q.id] === undefined`）与越界评分（`< 1 || > 5 || 非整数 || typeof !== "number"`）在一个 for 循环一次性抛出，违规题号会带在 message 里
- 这样保证下游累加器永远面对合法 `1..5` 整数，避免 NaN/字符串进入聚合污染 percentages

### 3.7 测试 fixture 形态
- 每维度 2 题（一正一反）= 10 题 мини题库，完全内联在 `score.test.ts`，不读 `data/questions/`，与题库工单（另一并行任务）解耦
- 2 题/维够用：可达到的百分比档位是 0% / 25% / 50% / 75% / 100%，其中 50% 是平局边界的关键命中点
- 真正的 32 题数据契约题库接入后，本引擎无需修改任何代码（消费 `QuestionBank` 接口）

### 3.8 vitest.config.ts 独立、不侵入 electron-vite 配置
- electron-vite 项目里 `package.json` 同时存在 `electron-vite.config.ts`（vite-plugin-react + electron 三入口）和 `vitest.config.ts`（纯 node + esbuild），两者互不引用
- vitest 启动时只读 `vitest.config.ts`，不会尝试编译 electron 主进程入口或 React 渲染入口 → 不会触发 `electron/main.ts` 之类需要 native runtime 的 import

## 4. 遗留问题

1. **vitest 1.6.1 在 Node 24 的 deprecation warning**：`The CJS build of Vite's Node API is deprecated`，来自 vitest 1.6 对 Node ESM 加载路径的内部 CJS fallback。不影响测试结果（49/49 PASS），但未来升级到 vitest 2.x 可消除。升级建议在 M2 完成 / 全量红线回归后一起做。
2. **`subtype` 命名空间被固定为 `stable` / `sensitive`**：UI/对话层（后续 M2 流程页 / M3 桌宠 / RAG 评测）需要 "坚定型 / 善感型" 的中文文案映射，本文件故意不预设（避免"渲染层 ↔ 引擎层" 互相依赖）。文案在交付 RAG 时由百科库 owner 提供。
3. **没做回归测试覆盖题库本身的合法形态**：例如 §1 要求 "每维 direction 双向各半、保证 16 型可达" 是题库工单（`docs/tech/M2-工单-题库.md`）的验收标准。本引擎只假设 `QuestionBank` 合规，未在 score.ts / score.test.ts 加 schema 校验。等题库正式工单并入后补一条 `bank.questions.length ≥ 2 * dimensions` 的断言。
4. **vitest.config.ts include 范围固定为 `src/scoring/**/*.test.ts`**：未来 M3 加新模块需要测试时，得改 include。建议在 vitest.config.ts 里加注释提示，但工单要求"min-change"，先不动。
5. **未加 `npm test` script**：工单只允许加 vitest 依赖、不强制加 scripts。`npx vitest run` 已能跑；CI 用法建议在主 agent 提交 PR 时一并加 `"test": "vitest run"`，避免工程师误用 `npm test` 触发默认 `electron-vite` 之类。
