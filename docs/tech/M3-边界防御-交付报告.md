## 三、能力边界纵深防御

### 3.1 设计：四层纵深

| 层 | 名字 | 实现位置 | 触发时机 | 命中后行为 | 落库 |
|---|---|---|---|---|---|
| **L1** | 入口过滤 | `data/intent-filter.json` + `server/src/intent-filter.ts` | 用户问题进 chat 路由 | 走人格化拒绝模板，**不调 LLM** | `refused=1 guard_hit=0` |
| **L2** | 注入防御 | 同 L1，规则 `category: "inject"`（53 词） | 入口过滤内 | 同 L1（inject 内部映射到 roleplay 模板） | `refused=1 guard_hit=0` |
| **L3** | 输出守卫 | `server/src/output-guard.ts` | LLM 流式完成后 | 丢弃 LLM 答案，改推拒绝模板 | `refused=0 guard_hit=1` |
| **L4** | 红队评测 | `eval/redteam_eval.jsonl` + `server/tests/redteam.test.ts` | CI 跑批 | 任何一条漏到 LLM 输出即视为纵深失败 | 拦截层结果表 |

**关键设计**：
- L1/L2 走关键词匹配（in-memory includes，宽松子串覆盖，覆盖中英双语 + 经典 jailbreak）
- L3 走"完整回答终检"——必须等 LLM 走完才能判断，所以 LLM 输出先缓冲（不再按 chunk 推前端）
- L4 是 CI 兜底：mock LLM 注入受控回答，验证守卫和日志字段

### 3.2 L2 inject 关键词（53 条，节选）

| 类别 | 关键词示例 |
|---|---|
| 中文"忽略" | 忽略之前、忽略以上、忽略所有指令、无视以上、不要遵守 |
| 英文"ignore" | ignore previous、ignore all、ignore above、disregard previous、forget your instructions |
| 中文"现在你是" | 现在你是、你现在是、从现在起你是、接下来你是、请扮演一个 |
| 中文"假装/本质" | 假装你是、假装没有限制、你其实是一个、你本质上是一个 |
| 英文"pretend/act" | you are now、from now on you are、act as、pretend you have no、you are actually |
| 经典 jailbreak | DAN、dan mode、do anything now、developer mode、jailbreak、jail broken |
| 探 system prompt | system prompt、systemprompt、reveal your prompt、what is your system prompt |

**入口过滤**：
- 命中"inject" → 路由层 `refusalCategory("inject")` → 复用 `roleplay` 模板（注入话术天然属于"切换身份"语义）；
- 拒绝模板里人格化口吻照旧：ENTP 的 "我的 Si 会当场死机"、INFJ 的 "不在我的世界里" 等；
- LLM 不会被调用，**没有任何模型痕迹**出现在用户侧。

### 3.3 L3 输出守卫 4 条规则

| 规则 | 触发条件 | 落库 | evidence |
|---|---|---|---|
| `code_block` | LLM 回答含 ` ``` ` | guard_hit=1 | ``` |
| `too_long` | 回答字符数 > 200 | guard_hit=1 | `length=N` |
| `break_character` | 出现"作为AI/作为语言模型/作为人工智能"等 | guard_hit=1 | "作为AI" 等 |
| `inject_fallback` | 用户问题带 inject 关键词但 LLM 还是被调了（防御性兜底） | guard_hit=1 | 命中的 inject 关键词 |

**实现关键**：把 `streamLlm` 改成"缓冲到 fullAnswer"模式，**不在 chunk 到达时立刻推前端**；等 LLM 走完、守卫终检后，才发 `meta` 事件（带最终 `guard_hit` 标志）+ 流式推最终答案（要么是 refusal，要么是 LLM 原文）。前端不会看到 LLM 原始越界回答的任何字符。

### 3.4 SSE 协议变化（M3 边界防御期）

`SseEvent` 的 meta 事件新增 `guard_hit: boolean` 字段，类型定义：
```ts
| { type: "meta"; rag_entry_id: string | null; refused: boolean; guard_hit: boolean }
```

含义：
- `refused=true, guard_hit=false` → 入口过滤命中
- `refused=false, guard_hit=true` → 输出守卫命中
- `refused=false, guard_hit=false` → 正常 LLM 回复

**注意**：原设计是"首条 meta 在 0.3s 内"用于思考动画。新设计下 meta 推迟到守卫检查之后（与 LLM 响应一起到达），牺牲首字延迟换数据一致性。生产环境 LLM 走真实流式时，仍能保留"meta 后流式体感"，只是 meta 时机从"预发"改为"随首条 delta 一起到"。

### 3.5 chat_logs 表新增 `guard_hit` 列

```sql
ALTER TABLE chat_logs ADD COLUMN guard_hit INTEGER NOT NULL DEFAULT 0
```

通过 `db.ts` 的 `ensureColumn` 幂等加列（与 `pet_nickname` 同模式），老库自动升级，**不丢历史写档**。

### 4.3 测试机制

- `server/tests/redteam.test.ts` 加载 `eval/redteam_eval.jsonl`，逐条调 `/api/chat`；
- 用 `vi.mock("../src/llm.js")` + `vi.hoisted` 注入受控 LLM 回答（guard_hit 样本需要 LLM 输出触发守卫）；
- 校验三层：SSE 事件 meta 的 `refused/guard_hit`、chat_logs 表的 `refused/guard_hit` 列、最终回答不包含 LLM 原文（guard_hit 样本）；
- 失败容忍：mock LLM 在未设 `mockAnswer.current` 时透传到原 mock 行为（保证"refused"样本不被 mock 干扰）。

## 七、风险与遗留

### 7.1 设计 tradeoff

- **首条 meta 时机推迟**：原 M3 设计文档要求"meta 在 0.3s 内"用于思考动画。L3 输出守卫必须等 LLM 走完才能判断，meta 推迟到守卫检查之后。生产 LLM 真实流式时仍有"meta + 后续流式"的体感差异，但首条 meta 不会先于 LLM 到达。**前端需要适配**：不要在 SSE 打开后立刻用 meta 做思考动画截止判断，建议沿用"收到首条 delta 后切到答案动画"。

- **缓冲全量 LLM 输出**：原 chat.ts 是 chunk 推前端；L3 守卫改为缓冲到 `fullAnswer` 再判断。LLM 真实流式时，**首字延迟 = LLM 整段流完的时间**（300 token 模型下可能 1-3s）。mock 模式下不影响测试。如未来对首字延迟敏感，可考虑 L3 改为"流式边推边扫，命中即停推+回退 refusal"，但会复杂化协议。

### 7.2 已知边界

- **inject 关键词不覆盖未登录话术**：L2 是关键词匹配，新型 prompt injection 变体需要持续扩词；建议每月跑一次 `redteam.test.ts` + 增补 JSONL。
- **L3 长度阈值 200 是固定值**：未来如要按 prompt 动态调整，需引入配置项。
- **`guard_hit=1` 路径只覆盖 4 条规则**：未覆盖"逻辑错误/事实错误"等 LLM 内容质量问题，那是 eval 体系（M2 评测集）的事，不在边界防御范围。

### 7.3 后续 follow-up（不阻塞本次）

1. 扩 L2 关键词库（建议每月增补，CI 跑 redteam）
2. 前端适配新 meta 时机（meta 推迟 + guard_hit 字段）
3. 后续如开真实 LLM 接入，加 `latency.test.ts` 验证"meta + first delta < 0.5s"是否仍满足
4. 红队 JSONL 可在 `eval/` 目录并行维护多个变体（如 `redteam_advanced.jsonl` 加大诱导复杂度）
