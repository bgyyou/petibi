## 2. 设计

### 2.1 旧 → 新 映射表（16 条）

旧四族色硬编码自色板 v3 的 `families`（与 `remap_portraits_v5.py` 同一套），新四族色实时读 `assets/style/palette.json`：

| 族 | 档位 | 旧色 | 新色 |
| --- | --- | --- | --- |
| analyst | shadow | `#3B2A4A` | `#42334A` |
| analyst | main | `#6B4E8E` | `#785D87` |
| analyst | light | `#9B7EC4` | `#A27EB6` |
| analyst | highlight | `#C9B4E0` | `#CC9EE6` |
| diplomat | shadow | `#1F4433` | `#224F3D` |
| diplomat | main | `#3E7C59` | `#3E8F6E` |

| diplomat | highlight | `#A8D5BA` | `#69F3BB` |

| sentinel | main | `#33608F` | `#399FB9` |
| sentinel | light | `#5B8FC7` | `#4DD7FA` |
| sentinel | highlight | `#9DC3E6` | `#92CAD8` |
| explorer | shadow | `#6B4A1F` | `#7D6D16` |
| explorer | main | `#A8763E` | `#E4C728` |
| explorer | light | `#D4A55F` | `#EBD55E` |
| explorer | highlight | `#F0CE9B` | `#F0E089` |

> 16 条映射全部 `old != new`，脚本据此建表。若未来某档位色值未变（old == new），该条不会进入映射表——避免无意义改写与干扰幂等判断。

### 2.2 算法

- 逐像素遍历 RGBA，命中旧色则改写为对应档位新色，**alpha 原样保留**（`src[x, y] = (new_r, new_g, new_b, a)`）。
- 透明像素（`a == 0`）直接 `continue`，不参与匹配 / 改写。
- 毛色 / 描边 / 中性色 / 透明像素一律不动；不透明像素但 RGB 不在旧 16 色集合内的也一律不动。
- `rglob("*.png")` 递归处理 `resources/sprites/` 全部子目录（含 `placeholder/`）。

### 2.3 幂等性来源

旧 16 色与新 16 色互不相交（逐位不同），第一遍运行后 PNG 里不再存在旧色，第二遍自然 0 命中 → 0 改写。

## 7. 遗留问题 / 诚实备注

- **族色跨 sprite 共存现象**：部分 sprite 同时使用了多族旧色，例如 INTP idle 既有 analyst `#6B4E8E` 也有 explorer `#D4A55F` / `#A8763E`。这是 sprite 设计本身的多族点缀（不是数据错误），脚本按 RGB 精确匹配对各族独立处理，结果与各族的 `families` 字段一致——没有按人格归属去猜测"应该改成哪族的 main"，避免引入与 palette.json 不一致的混合新色。
- **placeholder 使用 analyst 紫色族**：`make_placeholder.py` 硬编码 4 个 analyst 旧色，本次迁移后变为 analyst 新族 4 色。这是预期行为（占位图与正式 16 人格共用色板），不是 bug。
- **旧 16 色与新 16 色无重叠**：本次实现依靠该前提保证幂等。后续如果 palette.json 再次更新且某一档位色值巧合回退到旧 16 色之一，需要重审此脚本。
- **assets/art/ 未触碰**：本工单只针对 `resources/sprites/`。如果 `assets/art/` 下仍有色板外像素，需另开工单处理（v5 报告已确认 portrait-sheet 通过，未发现 sprites 范围之外的越界问题）。
