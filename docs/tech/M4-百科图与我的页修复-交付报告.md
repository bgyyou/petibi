## 2. P0-A：百科 Tab 16 人格形象图全部加载失败

### 2.1 根因

`src/panel/tabs/EncyclopediaTab.tsx` 通过 `window.petApi.spriteUrl(t, 'idle_0')` 拿形象图路径。
preload 的 `spriteUrl()` 返回**相对 URL** `sprites/<type>/<frame>.png`（沿用 M2 既有约定，不返回 file:// 硬编码）。

**生产（loadFile + file://）路径解析不一致**：

| 入口 | HTML 实际位置 | 相对 URL 解析到 | 是否存在 |
|---|---|---|---|
| 桌宠窗（pet） | `out/renderer/index.html` | `out/renderer/sprites/<type>/<frame>.png` | ✅ |
| **百科 Tab（panel）** | `out/renderer/panel/index.html` | `out/renderer/panel/sprites/<type>/<frame>.png` | ❌ |
| 重测结果页（setup） | `out/renderer/setup/index.html` | `out/renderer/setup/sprites/<type>/<frame>.png` | ❌ |

> 验证：`./node_modules/.bin/asar list release/win-unpacked/resources/app.asar | grep -E "(panel|setup|index)\.html$"` 确认三处 HTML 各自独立成目录；
> `... | grep sprites` 确认 sprites 只在 `out/renderer/sprites/...`（与 pet HTML 同级）。
> 因此 pet 正常、panel / setup 必然空白——owner 实测结果与之一致。

dev 模式（vite dev server，URL root = `src/`）下三个页面公用根，相对 URL 都解析到 vite 的 `publicDir`，
所以 dev 不暴露此问题，只在安装版炸。

### 2.2 修法

仿照 M4 海报生成已落地的 `portrait:read` IPC，把 sprite 也走 IPC 读盘 → 转 base64 data URL 返回，
渲染端 `<img src="data:image/png;base64,...">` 不依赖任何相对路径，pet / panel / setup 三处都能稳定显示。

**1) `electron/main.ts` 新增 `sprite:read` IPC handler**（位置在 `portrait:read` 后、`encyclopedia:read` 前）：

```ts
ipcMain.handle(
  'sprite:read',
  async (
    _event,
    args: { type: string; frame: string },
  ): Promise<string | null> => {
    if (!args || typeof args.type !== 'string' || typeof args.frame !== 'string') return null
    if (!MBTI_TYPE_RE.test(args.type)) return null
    if (!ALLOWED_SPRITE_FRAMES.has(args.frame)) return null
    const spritePath = join(
      RESOURCES_DIR,
      'sprites',
      args.type.toLowerCase(),
      `${args.frame}.png`,
    )
    try {
      const buf = readFileSync(spritePath)
      return `data:image/png;base64,${buf.toString('base64')}`
    } catch (err) {
      console.warn(`[main] sprite 读取失败：${spritePath}`, err)
      return null
    }
  },
)
```

+ 新增 `ALLOWED_SPRITE_FRAMES` 白名单常量（idle_0/1, blink_0/1, thinking_0/1），
  与 `src/pet-sprite.ts` 的帧表对齐，防止 `frame` 字段路径穿越；
+ 复用 M4-P0 已有的 `RESOURCES_DIR`（dev 走仓库根，prod 走 `process.resourcesPath`）。

**2) `electron/preload.ts` 在 `petApi` 暴露 `getSpriteDataUrl(type, frame)`**：

```ts
getSpriteDataUrl: (
  type: string,
  frame: 'idle_0' | 'idle_1' | 'blink_0' | 'blink_1' | 'thinking_0' | 'thinking_1' = 'idle_0',
): Promise<string | null> => {
  return ipcRenderer.invoke('sprite:read', { type, frame })
}
```

> 说明：保留 `spriteUrl()` 不动——桌宠窗仍走它，路径解析对得上无需改动；
>  本次只让 panel / setup 走新 IPC，blast radius 最小。

**3) `src/panel/tabs/EncyclopediaTab.tsx` 改为走 IPC**：

+ 模块级 `spriteDataUrlCache: Map<MbtiType, string|null>`（跨 list ↔ detail 复用，避免重复打 IPC）；
+ 列表页 mount 时 `Promise.all` 并发拉 16 帧 idle_0（每帧 ~1KB），结果存进 component state，
  按 type 取 `src={spriteDataUrls[t] ?? undefined}`，未加载完时渲染透明占位（alt 文字承担可达性）；
+ 详情页按 type 懒拉一次，命中缓存直接用。

**4) `src/setup/pages/ResultPage.tsx` 同步修复**——结果页也用 `spriteUrl()`，
setup HTML 在 prod 下走 `out/renderer/setup/index.html`，同样是相对路径死路；
改为挂一个 `useEffect` 拉 IPC data URL，渲染时按 `spriteSrc ? <img> : <div placeholder>` 二选一。

1. **路径验证**：`./node_modules/.bin/asar list release/win-unpacked/resources/app.asar | grep -E "sprites"` 输出
   `\out\renderer\sprites\enfj\idle_0.png` 等 96 条；panel / setup HTML 在 asar 内独立成目录；
   证明相对 URL 在 prod 下必坏 → 必须走 IPC。

2. **bundle 验证**：

3. **运行时验证**（理论）：

## 3. P0-B：「我的」Tab 卡在"加载中..."

### 3.1 根因

`src/api/client.ts`：

```ts
let USE_MOCK = (env.VITE_USE_MOCK_API ?? 'true') !== 'false'
```

旧默认值 `?? 'true'` 永远落到 `'true' !== 'false'` = `true`——**生产打包仍是 mock 模式**。

`src/panel/App.tsx` 启动链路：

```
panelApi.getInit() → 读 userData/profile.json（token + profile）  ✓
  ↓
  if (init.token && init.profile) {
    setToken(init.token)
    getMe(init.token)            ← 走到这里
      ↓ (USE_MOCK=true)
      mockGetMe(token)            ← 内部 mockUsers 是空的
        throw UNAUTHENTICATED     ← token 来自真接口 /api/auth/email/verify，
                                    mockUsers 找不到
    .catch → setUser(null)        ← user 永远是 null
  }
```

`App.tsx` renderTabBody（profile 分支）：

```tsx
if (!user || !token) {
  return <div className="profile-loading">加载中…</div>
}
```

user 永远为 null → 永远"加载中…" → 永远没有「重新测试人格」按钮 → 用户啥都干不了。

### 3.2 修法

**`src/api/client.ts` 三态显式解析 `USE_MOCK`**：

```ts
function resolveUseMock(): boolean {
  const v = env.VITE_USE_MOCK_API
  if (v === 'true') return true
  if (v === 'false') return false
  // 未显式设置：dev / 测试环境（env.PROD !== true）→ mock（沿用 M2 习惯，dev 不必起后端）；
  //              生产环境（electron-vite build）→ real（安装版用户期望连真后端）。
  return env.PROD !== true
}
let USE_MOCK = resolveUseMock()
```

三态语义：

| `VITE_USE_MOCK_API` | `env.PROD` | 解析结果 | 说明 |
|---|---|---|---|
| `'true'` | * | mock | 强制 mock |
| `'false'` | * | real | 强制 real |
| 未设置 | `true`（prod build） | **real** | ✅ 修复点 |
| 未设置 | `false`（dev / vitest） | mock | 沿用 M2 默认 |

> Vitest 行为：`import.meta.env.MODE='test'`，`PROD=false` → 走 mock 分支，保留原测试覆盖能力
> （既有 `chat-stream-e2e.test.ts` 等 4 个测试都依赖 `verifyEmailCode` 走 mock 拿 token，
> 跑了 `npm test` 全绿 318 通过即证）。

**附带 UX 改善（`src/panel/App.tsx`）**：

`getMe` 失败（server 未启动 / 鉴权失败 / 网络断）时记录 `userError`，
profile 分支的 loading 态会显示：

```
加载用户档案失败：<err.message>
请确认后端服务（端口 8787）已启动后重新打开主面板。
```

避免之前"永远加载中"——这是兜底，主修仍是 `USE_MOCK` 默认值。

### 3.3 验证

1. **smoke test**（把 `resolveUseMock` 抽出来跑一遍）：

2. **bundle 验证**（确认 Vite 把 `__vite_import_meta_env__ = { "PROD": true }` 内联进 prod 包）：

   加载即 `USE_MOCK = false` → `getMe(token)` 走 `realGetMe(token)` → 命中后端 `GET /api/me` → 正常返回 user → ProfileTab 渲染 → 「重新测试人格」按钮可见。
