## 1. 背景与目标

### 1.1 改造前问题
- `routes/chat.ts` 为做输出守卫把 LLM 回答**全缓冲**后再推，破坏了 PRD §3.4
  "首字 ≤2s / meta 事件 0.3s 内用于思考动画"的流式体感。
- 全平台统一硬编码 `≤150 字` 一刀切，对长输入（≥150 字含背景叙述）的深度倾诉场景不够用，
  对闲聊场景又过宽（闲聊可以更短）。
- `scripts/check_personas.py` 的意图类别清单硬编码为 5 类，落后于
  `data/intent-filter.json` 现行的 6 类（code / homework / generate / web / roleplay / inject）。

### 1.2 目标（owner 工单要求）
1. 校验脚本同步：动态读取 intent-filter.json 的 6 类；inject 关键词数上限放宽到 60。
2. 输出守卫改**流式 + 增量**：meta 立即发 / LLM token 边推边检 / 硬截断发 guard 事件 /
   软截断追加省略号。
3. 回复长度三档制（闲聊 ≤80 / 标准 ≤150 / 深度 ≤400）+ 深度档三段式 prompt 指令。

### 2.2 任务 2：流式 + 增量守卫

#### SseEvent 契约扩展（`server/src/types.ts`）
- `meta`：`guard_hit` 仍存在，**前置检查通过后立即发**，此时 LLM 还没机会输出，
  `guard_hit=false`（前端照常启动思考动画）。
- 新增 `guard` 事件：`{ type: "guard"; reason: string; text: string }`，
  mid-stream 截断标识，text 是该人格的拒绝模板。
- `done`：`guard_hit` 字段最终化，反映本次是否被守卫命中（供 chat_logs 写入 + UI 最终确认）。

#### 流式守卫实现（`server/src/output-guard.ts`）
- 新增 `createStreamGuard(tierLimit)`：
  - 内部维护 `buffer / softLimitReached / ellipsisSent / hardStop`。
  - `feed(delta)` 单次增量检查：
    - 硬截断 1：buffer 含 ` ``` ` → `code_block`。
    - 硬截断 2：buffer 含"作为AI / 作为语言模型 / 作为人工智能"等 → `break_character`。
    - 硬截断 3：buffer 长度 > `tierLimit × 1.2`（向上取整）→ `too_long`。
    - 软截断：buffer 长度 ≥ `tierLimit` → 标记 softLimitReached（路由层在发完本 delta
      后追加 `……` 省略号，不计 guard_hit）。
  - 保留旧 `applyOutputGuard(question, answer, filter, options?)`：
    - 默认 `maxLength=200`（向后兼容，redteam 单测不动）。
    - chat.ts 终检时传 `{ maxLength: hardLimitFor(tier) }`，与档位制一致。
- 档位常量集中：
  - `TIER_MAX_CHARS = { chitchat: 80, standard: 150, deep: 400 }`
  - `TIER_MAX_TOKENS = { chitchat: 160, standard: 300, deep: 800 }`
  - `hardLimitFor(tier) = Math.ceil(TIER_MAX_CHARS[tier] × 1.2)`
  - `decideReplyTier(question, filter)`：先看 rag_skip_patterns → chitchat；
    否则 `trimmed.length >= 150` → deep；其余 standard。

#### 路由实现（`server/src/routes/chat.ts`）
- 流程重写：鉴权 → profile → SSE 头 → 意图过滤 → 配额 → RAG →
  **档位判定** → **立即发 meta**（不等 LLM）→ 拼 prompt（含档位指令）→
  **流式调 LLM + 增量守卫**。
- 增量守卫循环：
  ```ts
  for await (const chunk of streamLlm(...)) {
    if (chunk.done) break
    const r = guard.feed(chunk.delta)
    if (r.hardStop) { sseWrite({ type: "guard", reason, text: refusal }); break }
    if (guard.isEllipsisSent()) continue
    sseDelta(chunk.delta)
    if (guard.isSoftLimitReached()) {
      sseDelta("……")
      guard.markEllipsisSent()
    }
  }
  ```
- 流式结束后做**终检兜底**（`applyOutputGuard` + 档位 hardLimit），
  扫一次 question 是否带 inject 关键词漏到 LLM（理论上入口已拒，
  纵深防御）。
- 落 `chat_logs`：refused 仍为 0、guard_hit 在硬截断/终检命中时记 1。
- 发 `done` 事件（带最终 `guard_hit` 与 `total_chars`）。

## 3. 关键设计决策与权衡

### 3.1 为什么 meta 立即发 + guard 事件分离
- **meta 立即发**：让前端在 LLM 还没出字时就启动思考动画，恢复 PRD §3.4 的 0.3s 体感。
- **guard 单独事件**：meta.guard_hit 此时一定是 false（LLM 没机会输出），
  把"截断信号"独立成 `guard` 事件让前端在 mid-stream 立即切到拒绝模板。
- **done.guard_hit 最终化**：给 chat_logs 写入和 UI 终态确认用。

### 3.2 为什么软截断追加 "……" 而非掐断
- "超过档位上限未达 1.2 倍"是**温和终止区**（多 1-19%），属可接受范围。
- 掐断 = 触发 guard_hit=1 + chat_logs 标守卫命中 = 误报。
- 加省略号让用户清楚"还有内容但被截了"，前端可读 "……" 自然结束；不污染守卫统计。

### 3.3 为什么 inject_fallback 兜底还保留
- 入口意图过滤在 chat.ts 早于 LLM 调用就拒了 inject 类，正常流程 LLM 不会拿到 inject 问题。
- 但作为**纵深防御**，流式结束后终检再扫一次 question，避免入口过滤词库更新但代码未同步等异常路径漏到 LLM。
- 单测 `redteam.test.ts` 的 `applyOutputGuard：inject_fallback 命中` 用例继续通过。

### 3.4 为什么 applyOutputGuard 接受可选 maxLength
- 默认 200 保持向后兼容（redteam 4 条单测不动）。
- chat.ts 终检传 `hardLimitFor(tier)`，让终检阈值与档位制一致。
- 否则深度档（hardLimit=480）的 LLM 输出会在终检被 200 阈值误判为 too_long。

## 9. 终审修订：`check_eval.py` 适配三档制

### 9.1 触发原因
终审发现追加 5 条 `tier: "deep"` 用例后，`python scripts/check_eval.py` 失败 7 处：
- 1 处总条数（85 ≠ 80）
- 5 处 deep id 格式不符（`eval-deep-intj-01` 等）
- 1 处"重复组合"（5 个 deep 与对应 standard 同 (personality, scenario)）

校验器按旧契约硬卡"总条数=80、id 单一格式、组合唯一"。

### 9.2 修复（仅改 `scripts/check_eval.py`）

| 规则 | 旧契约 | 新契约 |
|---|---|---|
| 总条数 | = 80（统一硬约束） | 标准档 = 80 + 深度档任意（独立计数） |
| id 格式 | `eval-<lowercase>-<NN>` 唯一 | 标准档 `eval-<lowercase>-<NN>`（序号 01-05）<br>深度档 `eval-deep-<lowercase>-<NN>`（序号两位数即可，可 > 05） |
| tier 字段 | 无 | 缺失视为 standard；非法值报错；deep 必须 question ≥150 字（与 `decideReplyTier` 阈值对齐） |
| 16×5 组合唯一 | 全 80 条统一检查 | **仅对标准档生效**；深度档允许与标准档同 (personality, scenario) |
| 16 人格各 5 / 5 情境各 16 | 全 80 条 | **仅对标准档生效** |
