## 一、范围与边界

### 1.1 本工单做什么

- 提供客户端海报生成能力（1080×1350 Canvas 2D 绘制，**纯本地**）
- 聊天 Tab 每条完成态 assistant 消息旁加「生成海报」按钮 → 预览弹窗
- 弹窗内支持「保存本地（PNG 下载）」+「分享到广场」
- 调 server 端两个并行工单接口：海报上传（`POST /api/posters`）+ 分享计数（`POST /api/me/share-count`）
- 提供像素级校验脚本（`scripts/check_poster.py`）防止下次改模板时漏画水印/品牌

### 1.2 不做什么（边界外）

- 不动 server 端（接口由并行工单实现，本工单只走契约）
- 不动 setup 窗（setup 阶段还没有对话历史可生成）
- 不做深度定制模板（V1 单模板足以覆盖 90% 场景；V2 再开放多模板）
- 不做深度档回答的"摘要算法"（按 PRD §3.4 三段式：复述确认 / 人格分析 / 建议，取前 3 段拼起来即可）

## 二、布局分区（设计稿描述）

海报 1080×1350（小红书 3:4），自上而下分 4 个区域：

| 区域 | y 范围 | 高度 | 内容 |
|---|---|---|---|
| 顶部品牌条 | 0 ~ 110 | 110px | 深色族色（`family.main`）底；左 `Petibi` 品牌名（48px 700），右主 Slogan「遇事不决，问问你的人格」（28px 500） |
| 人格卡片 | 110 ~ 660 | 550px | 白色圆角卡 + 族色描边 + 阴影；左 360×360 portrait（persona 大字 + 动物名首字作为缺失兜底），右 MBTI 类型大标 + 动物 + 昵称 + 像素分隔线 + 小字装饰 |
| 对话精选 | 660 ~ 1180 | 520px | 区块标题「💬 这次对话」；用户问题气泡（右对齐，深色底白字）；桌宠回答气泡（左对齐，白底族色描边）；深度档回答按 PRD §3.4 三段式取前 3 段 |
| 底部水印 | 1180 ~ 1350 | 170px | 像素风虚线分隔；副 Slogan「像你这样的人，通常会怎么做」居中（族色 30px 600）；下方 `Petibi · YYYY-MM-DD` 灰字；四角像素星呼应桌宠 8fps 像素美学 |

整体风格：
- **背景**：`lighten(family.main, 0.82)`（族色与白按 82% 调和，呼应 `palette.light` 字段），既保持族色识别度又柔和不刺眼
- **像素风元素**：四角 8×8 像素星 + 虚线像素分隔条（4px 厚 12+8 间距），与桌宠 sprite 8fps 像素美学统一
- **圆角处理**：4 个 24px 圆角 + 4 个角方块"伪圆角"近似，跨平台一致（不依赖 canvas `roundRect` API）

## 四、关键设计决策

### 4.1 portrait 资产的运行时桥接

**问题**：portrait（512×512 闭源美术资产）放在 `assets/art/portraits/`，vite publicDir 只覆盖 `resources/`，渲染进程不能直接 `<img src>` 加载；又因为是闭源版权资产，不能复制到 `resources/` 公开打包。

**方案**：扩展 `petApi.getPortraitDataUrl(type)`，主进程 `ipcMain.handle('portrait:read', ...)` 走 fs 读 PNG 转 `data:image/png;base64,...` 返回渲染进程；16 型白名单正则防路径穿越。

**为什么不用 file:// 硬编码**：跨平台路径分隔符差异 + 打包后 out/ 目录结构变化，硬编码路径会失效；data URL 在浏览器/electron 都 100% 兼容。

### 4.2 纯函数 drawPoster + 异步 generatePoster 分离

- `drawPoster(ctx, input)` 是纯同步函数：所有渲染决策（坐标 / 颜色 / 文本换行）都在这里；接受抽象的 `PosterCanvasContext` 接口。
- `generatePoster(input)` 是异步包装：负责拿 canvas / 异步加载 portrait / 转 Blob。

**好处**：
- `drawPoster` 可以在 node-canvas 上跑（自验脚本直接用），不需要 Image + onload
- 文本换行 / 截断 / 蒸馏全部走纯函数，vitest 单测覆盖零成本
- 浏览器 / Electron 端走 `generatePoster` 一键完成，符合上层 UX 直觉

### 4.3 状态机而非分散 useState

海报弹窗 5 个阶段（`generating` / `preview` / `sharing` / `shared` / `failed`）用单一 `PosterModalState` discriminated union，避免按钮 disabled 判断、错误展示、URL revoke 等逻辑分散到多个 useState 里导致状态不一致。

### 4.4 失败不毁体验

- 海报生成失败 → 切 `failed` 态，仍展示「保存本地」按钮（blob 为空时按钮 disabled），用户至少能看到原因
- 分享到广场失败 → 切 `failed` 态，blob 仍可保存本地兜底
- bumpShareCount 失败 → 静默（不阻塞主分享流程，因为是 V2 装扮解锁的预埋数据）

### 4.5 端到端实测远超 REVIEW 阈值

实测端到端（含 PNG 编码）P95 = 46.8ms，REVIEW 阈值 3000ms，**余量 64 倍**。原因是：
- portrait 512×512 → 360×360 缩放，单次 drawImage 极快
- 字体光栅化第二次起走缓存
- 文本拆行按字符流式算，不依赖 measureText
- 没引入任何外部图像处理库

## 七、未完成 / 留给后续

1. **真接口未实现**：本工单只是客户端，server 端 `POST /api/posters` 和 `POST /api/me/share-count` 由并行工单交付。当前 mock 模式（`VITE_USE_MOCK_API` 默认 true）下 dev 可走通；切到 real 模式前需 server 端先就绪。
2. **多模板**：V1 单模板够用；V2 可考虑"深色 / 浅色 / 节日"等多模板切换。
3. **机审回调**：海报上墙后 server 端机审改 status（pending → approved / rejected），本工单不涉及。
4. **装扮解锁消费**：V2 `bumpShareCount` 累计值会被装扮系统消费；本工单只负责写入。
5. **真实 Electron 环境验证**：本自验在 node-canvas 上跑，Electron BrowserWindow 里 Image.onload + toBlob 路径未实跑；dev 起来后第一次点「生成海报」时若有 IPC 异常会落入弹窗 `failed` 态，仍可保存本地。
