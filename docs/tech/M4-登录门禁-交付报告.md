## 2. 改动清单（按文件）

### 2.1 `electron/main.ts`

新增两个**纯函数**便于测试钉死：

- `isJwtUsable(token)`：启动期 token 快筛。解析 JWT 三段、读取 payload.exp、判定是否 > 当前时间。**不做签名校验**——签名由 server `/api/me` 严格校验，本函数只做"已过期就别直接进桌宠"的快筛。
- `decideStartupWindow({ hasProfile, hasUsableToken, isGuest })`：
  - `pet`   ：profile 完整 + token 可用 → 桌宠
  - `panel` ：profile 未初始化 + guest 标志 → 仅面板（**不**开桌宠）
  - `setup` ：其它情况 → setup 登录页

`app.whenReady()` 与 `app.on('activate')` 改用 `decideStartupWindow()` 决策，不再写死 `if (profile.mbti) createPetWindow()`。

`setup:enter-guest`（"先逛逛"）改写：原本走 `transitionSetupToPet()` 会拉起 pet 窗——这违反 ISSUES P2-025。**新版本只关 setup + 开 panel，不调 pet 窗**。

新增两个 IPC：

- `panel:logout`（来自「我的」Tab）：清本地 token（保留 profile 字段便于 UX）+ 隐藏 pet + 打开 setup 登录页。
- `panel:auth-expired`（来自 panel App.tsx 的 setAuthInvalidHandler）：token 失效时主进程执行与 logout 等价的"隐藏 pet + 开登录页"动作。

### 2.2 `electron/preload.ts`

`panelApi` 暴露两个新方法：

- `panelApi.logout()` → 触发 `panel:logout`
- `panelApi.notifyAuthExpired()` → 触发 `panel:auth-expired`

### 2.3 `src/panel/tabs/ProfileTab.tsx`

- 新增"账号"卡片 + 「退出登录」按钮 + 像素风确认弹窗（复用 retest 弹窗的样式 .profile-retest-modal 系列）。
- 退出登录走 `window.panelApi.logout()`。
- 仅登录态可见——访客态该 Tab 已被 `GuestLock` 锁定。

### 2.4 `src/panel/App.tsx`

`setAuthInvalidHandler` 回调新增一行：调 `window.panelApi.notifyAuthExpired()` 通知主进程隐藏桌宠 + 拉起登录页。本地 token 清理由 panel 端负责（避免与主进程写竞态）。

### 2.5 `server/src/config.ts`

无需改动——`jwtExpiresInSec` 默认为 `60 * 60 * 24 * 30`（30 天），与工单要求一致。本工单新增 server 测试钉死这一点。

## 3. 取舍说明

### 3.1 退出登录后保留 profile 字段？

**保留。** 理由：

1. 老用户退出后想重新登录时，setup 流程由 LoginPage 控制（dispatch `LOGIN_SUCCESS` → nickname 步骤），不会跳过任何步骤；保留 profile 字段不会让用户"被当成已注册用户自动跳过测试"。
2. LoginPage 已实现"老用户直通"路径（user.mbti 已存在 → 直接 `setProfile` + `completeSetup`）；profile 字段保留能让重新登录成功后写回是"合并"而非"全新"，避免 `/api/me/profile` 409（profile 已写又被重写）。
3. UX 落差更小：用户看到"自己的资料"被一并清掉会困惑。

测试 `login-gate.test.ts` 钉死这条性质："退出登录：writeProfile({token:null, profile:kept}) 后 readProfile 拿到 token=null 但 profile 不变"。

### 3.2 token 验证为何不做签名校验？

`isJwtUsable()` 仅检查 payload.exp，**不**调用 `jwt.verify(token, secret)`。理由：

1. **快筛**：启动期每条 token 都跑一次签名校验要 IO + 计算，启动成本不值得——签名校验由 server `/api/me` 在用户首次请求时做严格校验。
2. **降级兜底**：即使本地 token 被篡改，server `/api/me` 返回 401 → `setAuthInvalidHandler` 兜底清理 + 引导重登。
3. **不引入新依赖**：main.ts 不需要 jsonwebtoken 依赖（package.json 已有，但 import 进 main 模块会让 vite build 多打一个 chunk）。

### 3.3 半完成态（token 有 + profile 无）走 setup 而非 pet

理论上 token 可用意味着 server 已签发；profile 缺失意味着用户在 setup 流程中途中断。**让 setup 流程自动续接**（LoginPage 老用户直通 / 新用户 nickname），而不是强行开 pet 后让桌宠没有 sprite 路径可渲染。决策表中这一项走 setup 而非 pet。

## 5. 后续可选改进（不在本工单范围）

1. **主动登出远端**：`panel:logout` 只清本地 token，server 端不感知。当前 MVP JWT 是无状态的（M2 决策），无吊销表。如果未来要加"踢下线"，需新增 server `/api/auth/logout` + JWT 黑名单。
2. **token 刷新**：30 天过期后强制用户重输验证码体验略生硬；可在 token 临期（如剩 3 天）自动调 server 静默续签。
3. **guest flag 与 profile 的互斥**：当前两者独立存储，未来 LoginPage 完成时建议主动 `setGuestFlag(false)`，避免 profile 已有但 guest 标志仍残留。

# 追加：owner 实测两个新问题 — Bug 1 / Bug 2 修复

> M4 P2-025 owner 二次实测反馈的两个问题。
>
> - **Bug 1**：重测换人格报「重复写档不在 MVP 范围内」（server 409）；
> - **Bug 2**：登录成功（已有档案的老用户）后主面板和桌宠要一起出现（现状只出桌宠）。

---

## Bug 1 根因 + 修法

### 根因

`server/src/routes/me.ts` 的 `POST /api/me/profile` 写档逻辑在 M2 工单里被设计为"已写档 → 409 拒绝二次写入"，注释明确写"重复写档不在 MVP 范围内"。但 M4 重测人格（`ResultPage` retest 模式）会再次调 `saveProfile` 把 mbti/subtype 写回 server，这条链路在 server 端就 409 了。重测流程的 server 同步走的是 `client.ts:realSaveProfile → POST /api/me/profile`，与初次注册走的是同一个端点。

修复前 `server/src/routes/me.ts:240-251`：
```typescript
const existing = findUserOrThrow(db, userId)
if (existing.mbti && existing.nickname && existing.subtype) {
  throw new AppError(409, ErrorCodes.InvalidProfile, "已写档，重复写档不在 MVP 范围内")
}
```

### 修法

将 `POST /api/me/profile` 改为 **UPSERT 语义**：已存在的用户允许覆盖 mbti/nickname/subtype（更新而非 409 拒绝）。防并发误用的基本校验保留：

- 必须鉴权（`requireAuth` 中间件）；
- body 字段必须有合法 nickname / mbti / subtype（`validateProfile`）；
- 用户必须存在（`findUserOrThrow` 抛 404，不暴露档案）。

```typescript
router.post("/profile", (req, res, next) => {
  try {
    const userId = userIdFromRequest(req)
    findUserOrThrow(db, userId)            // 用户不存在 → 404
    const profile = validateProfile(req.body)
    db.prepare(
      "UPDATE users SET nickname = ?, mbti = ?, subtype = ? WHERE id = ?",
    ).run(profile.nickname, profile.mbti, profile.subtype, userId)
    // ...返回最新 user 视图
  } catch (err) { next(err) }
})
```

为什么是 UPSERT 而不是新增 `POST /api/me/profile/update`：

1. **接口最小化**：M2 以来前端只认 `/api/me/profile` 这一个端点，新增路径要改 `client.ts` + setup 渲染端 + retest 流程三处；
2. **语义对齐**：MVP 阶段"写档"已经覆盖了"首次写档 + 重测更新"两个场景，单一端点 UPSERT 更直观；
3. **校验统一**：`validateProfile` 一处，nickname 长度/mbti 白名单/subtype 取值都在一处管；
4. **不引入并发风险**：写档本质是"覆盖式 UPDATE"，单用户串行；并发场景下后写者赢，与原 409 兜底相比反而更可预测。

副作用：原来钉死的"重复写档 → 409"测试要改为钉死 UPSERT（`server/tests/auth.test.ts` 已更新）。

## Bug 2 根因 + 修法

### 根因

老用户登录（`LoginPage.tsx` 检测到 `res.user.mbti` 已存在）走"老用户直通"路径：写本地 profile + 调 `window.petApi.completeSetup()`。`completeSetup` 在主进程触发的是 `transitionSetupToPet()`，**只**创建 pet 窗，不创建 panel 窗。owner 实测反馈"主面板和桌宠要一起出现"——桌面宠物应用的"常伴面板"姿态未对齐。

新用户首次初始化走 `ResultPage` 也调 `completeSetup`，同样只出 pet。这条对**新用户**是正确的（首次看到桌宠是惊喜，面板由用户主动单击 pet 唤回更聚焦）；但**老用户**已经熟悉产品，登录后应该立即看到 pet + panel。

修复前 `LoginPage.tsx:75-90`：
```typescript
if (res.user.mbti) {
  await window.petApi.setProfile({...})
  window.petApi.completeSetup()       // 仅 pet，无 panel
  return
}
```

### 修法

新增 preload API `petApi.completeSetupForExistingUser()`，对应主进程 IPC `setup:complete-existing-user`。与 `setup:complete` 的关键差异：

- **`setup:complete`**（首次注册）：仅开 pet，panel 由用户主动单击 pet 唤出。
- **`setup:complete-existing-user`**（老用户登录）：同时开 pet + panel，setup 关闭。

主进程 IPC 实现要点（顺序与 P0-006 修复同源）：

1. 先建/显示 pet（保证任一时刻至少有一个窗口）；
2. 用 `setupClosingForTransition = true` 标记关 setup（避免被判定为"用户放弃初始化"导致 app.quit）；
3. 再开 panel（懒加载/复用）。

`electron/preload.ts`：
```typescript
completeSetupForExistingUser: (): void => {
  ipcRenderer.send('setup:complete-existing-user')
},
```

`electron/main.ts`：
```typescript
ipcMain.on('setup:complete-existing-user', () => {
  if (!petWin || petWin.isDestroyed()) createPetWindow()
  else if (!petWin.isVisible()) petWin.show()
  petHidden = false
  petWin?.webContents.send('pet:visibility', false)
  refreshTrayMenu()
  if (setupWin && !setupWin.isDestroyed()) {
    setupClosingForTransition = true
    setupWin.close()
  }
  setupWin = null
  createPanelWindow()
  if (panelWin && !panelWin.isVisible()) {
    panelWin.show()
    panelWin.focus()
  }
})
```

`LoginPage.tsx` 老用户分支改调 `completeSetupForExistingUser`。
