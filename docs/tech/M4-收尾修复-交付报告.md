## 3. 关键设计决策

### 3.1 为什么用「显式 onMinimize / onClose props」而不是「运行时类型断言」？

原 TitleBar 实现：
```ts
function handleMinimize(): void {
  const fn = (window as unknown as {
    petApi?: { minimizeSetup?: () => void; minimizePanel?: () => void }
  }).petApi
  if (fn?.minimizeSetup) fn.minimizeSetup()
  else if (fn?.minimizePanel) fn.minimizePanel()
}
```

问题：
1. **依赖运行时 document.title**：`document.title === 'Petibi'` 是脆弱字符串匹配（panel 标题碰巧是 'Petibi'）；如果未来某窗口 title 改成 'Petibi 主面板' 就直接错。
2. **类型断言链 `(window as unknown as { petApi?: ... })`**：TypeScript 看不到真实 API 表面，新增 IPC 通道时 IDE 不会提示。
3. **按钮 onClick 链路依赖父级 drag 区域不拦截 mousedown**：实测发现某些 Electron 版本下父级 `-webkit-app-region: drag` 会吞子元素 mousedown，button 的 onClick 不触发——这是 owner 实测"最小化键无反应"的根因。

收尾修复：
- 调用方显式传 `onMinimize` / `onClose`（强类型，无运行时字符串比较）；
- 按钮 `onMouseDown={swallowDragArea}` 显式 stopPropagation 兜底；
- CSS 加 `-webkit-app-region: no-drag` 双重保险。

### 3.2 为什么 BackButton 用 `flex: 0 0 auto` + 升级字号到 13px？

owner 实测反馈"看不到返回键"。原 `.setup-back` 用 `align-self: flex-start`（OK），但 setup-shell 是 flex column、setup-body 是 `flex: 1 1 auto; overflow-y: auto`。当 4×4 人格卡片填满 setup-body 时，flex 收缩可能把 setup-back 挤到几乎不可见。

修复：
- `flex: 0 0 auto` — 强制不被压缩（始终完整显示）；
- 字号 12px → 13px、padding 6px×12px → 8px×14px、box-shadow 2px → 3px（在 800×640 setup 窗里更显眼）；
- `z-index: 5` → `20`（确保不被 setup-header 覆盖）。

### 3.3 为什么单击/双击用纯函数状态机？

owner 提的"延迟 250ms 内无第二次点击才触发单击菜单"是经典 debounce + 状态机问题。如果直接用 `setTimeout` 写，逻辑会散在事件 handler 里；测试也困难。

收尾修复抽出 `feedClick(state, event)` 纯函数 + `DOUBLE_CLICK_THRESHOLD_MS = 250`：
- 状态：`idle` / `pending` 两种；
- 事件：`click` / `fire-pending` / `reset`；
- 输出：`{ next, action, clearTimer }`。

App.tsx 在 mouseup 时调 `feedClick(clickState, { type: 'click', timestamp: Date.now() })`，根据返回的 `action` 决定派发什么；返回 `clearTimer: true` 时清掉之前的 250ms 计时器（避免双击时"先弹菜单再关"的闪烁）。

### 3.4 为什么 tray.on('double-click', ...) 接受"双击同时触发 click + double-click"？

Windows Tray 的 `click` 和 `double-click` 事件互不互斥——操作系统层面双击会派发两次 click + 一次 double-click（系统级双击阈值由 Shell 控制，不是 Electron 能干预的）。

收尾修复在双击 handler 内调 `showPet() + showPanel()`，与单击 handler 调 `showPet()` 重叠。`showPet()` 是幂等的（内部判 `if (petWin.isDestroyed()) createPetWindow(); else if (!petWin.isVisible()) petWin.show();`），所以两次调用不会出错。

设计上接受这个"双击既会唤起桌宠又会打开面板"的行为——因为这正是 owner 期望的"双击托盘 → 显示桌宠 + 打开主面板"路径。

### 3.5 为什么 LoginPage 没有 BackButton？

按上一单（M4 setup 返回导航）"3.5 为什么不改 LoginPage"决策保留：
- login 是流程起点，没有"上一步"语义可点；
- 新增返回按钮会让用户以为还有"上一步"，违反"登录是流程起点"的契约。

CDP 验收脚本里 `backBtnOnLogin === false` 是**期望 true**（即无返回键是设计正确的）。
