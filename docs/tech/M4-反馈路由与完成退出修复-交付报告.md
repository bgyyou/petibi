## 1. Bug 2 复现过程（工单要求：先复现再修）

前两轮修复都在渲染进程 reducer 层（`FEEDBACK_RECORDED` 不动 step、白名单 action 等），没打中——因为触发点根本不在渲染进程。这一轮先建了一个能真实驱动 Electron 的复现脚本：

**`scripts/repro-setup-complete.mjs`**（新增）
- 用独立 `--user-data-dir` 临时目录启动应用（保证走 initial setup 分支，不污染真实档案）；
- 开 `--remote-debugging-port=9333`，用 CDP 连上 setup 窗，`Runtime.evaluate` 执行 `window.petApi.completeSetup()`——**等价于用户在结果页点「完成，去和我的桌宠玩」的最后一步**；
- 观察主进程是否退出、setup 窗是否关闭、桌宠窗是否出现。

### 1.1 修复前（复现成功）

```
[repro] setup 窗已就绪：file:///.../out/renderer/setup/index.html?mode=initial&initialStep=pick
[repro] completeSetup 调用结果："sent"
[main] [main] 正在关闭内嵌 server...
[main] [main] 内嵌 server 已关闭，退出应用
[repro] 主进程退出，code=0
[repro] ❌ 复现 P0-006：调用 setup:complete 后主进程整个退出了 (exit code=0)
```

主进程日志里 `正在关闭内嵌 server...` 来自 `app.on('before-quit')`——说明确实是 `app.quit()` 被调用了，不是崩溃。

### 1.2 调用链定位

```
渲染进程 ResultPage「完成」按钮
  → window.petApi.completeSetup()            (electron/preload.ts:200)
  → ipcMain.on('setup:complete')             (electron/main.ts)
  → transitionSetupToPet()
      → setupWin.close()
        → setupWin.on('closed')  ← 这里：mode==='initial' && !isShuttingDown → app.quit()
```

`'closed'` 回调闭包捕获的是**创建窗口时的 mode**，`transitionSetupToPet()` 里那句 `setupWin = null` 完全不影响它，所以"主进程主动关窗"和"用户手动关窗"在这个回调里**根本无法区分**——这就是三轮没修掉的原因。

### 1.3 修复后（同一脚本，同一链路）


## 3. 各 bug 修复明细

### 3.1 Bug 1：`POST /api/me/feedback`

**新表 `test_feedback`**（`server/src/db.ts`，`ensureSchema` 内幂等建表）：

```sql
CREATE TABLE IF NOT EXISTS test_feedback (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL,
  mbti TEXT NOT NULL,
  subtype TEXT NOT NULL,
  accepted INTEGER NOT NULL,
  comment TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
CREATE INDEX idx_test_feedback_user ON test_feedback(user_id, created_at);
CREATE INDEX idx_test_feedback_mbti ON test_feedback(mbti, accepted);
```

`idx_test_feedback_mbti` 是给题库迭代最常用的口径准备的：某人格的「测不准率」= `SELECT mbti, AVG(accepted) FROM test_feedback GROUP BY mbti`。

**路由契约**（挂在 `/api/me` 下，走 `requireAuth`）：

| 项 | 值 |
|----|----|
| 请求 | `POST /api/me/feedback`，body `{ mbti, subtype, accepted: boolean, comment?: string }` |
| 成功 | `200 { ok: true, recorded_at: "YYYY-MM-DD HH:MM:SS" }` |
| 参数非法 | `400 INVALID_FEEDBACK`（accepted 非布尔 / mbti 不在 16 型 / subtype 非法 / comment 非字符串或 >200 字） |
| 未鉴权 | `401 UNAUTHORIZED` |

设计取舍：
- **mbti/subtype 由前端传，不从 users 表反查**——用户可能反馈完不点「完成」，此时 users 表还是旧人格，反查会把反馈算到错的人格头上；
- **不做 UNIQUE**：同一用户多轮测评的多次反馈全部留痕，题库迭代要看时间序；
- **只写库，不动 users**，也不触发任何窗口/流程状态变更（沿用 P0-006 红线，测试里有一条专门钉死）。

前端契约同步改成 `{ mbti, subtype, accepted }`（原来只传 `{ match }`），`ResultPage` 直接用结果页正在展示的 `resultType` / `resultSubtype`。

### 3.2 Bug 2：点「完成」应用退出

判定逻辑收敛成一个纯函数（`electron/main.ts`）：

```ts
export function shouldQuitOnSetupClosed(ctx: {
  mode: 'initial' | 'retest'
  isShuttingDown: boolean
  transitioningToPet: boolean
}): boolean {
  if (ctx.isShuttingDown) return false      // 已在退出流程，不重复 quit
  if (ctx.transitioningToPet) return false  // 主进程主动切窗 = 正常完成【根因】
  return ctx.mode === 'initial'             // 用户手动关 initial 窗才是"放弃初始化"
}
```

配套两处改动：
1. `transitionSetupToPet()` 关窗前置 `setupClosingForTransition = true`，`'closed'` 回调消费后立刻复位；`createSetupWindow()` 建窗时也复位一次（防止窗口已销毁导致 `'closed'` 不触发时 flag 泄漏）；
2. `transitionSetupToPet()` 改成**先建桌宠窗、再关 setup 窗**——任一时刻至少有一个窗口存活，既不会瞬时触发 `window-all-closed`，用户观感也正好是"点完成 → 桌宠直接出现"。

覆盖到的两条 transition 路径：`setup:complete`（正常完成）与 `setup:enter-guest`（访客模式"先逛逛"）。`setup:retest-complete` 走的是 `mode='retest'`，本来就不退出，行为不变。

### 3.3 Bug 3：动物名"未知"

`server/src/personas.ts` 新增：

```ts
export function resolvePersonasDir(personasDir?: string): string {
  if (personasDir) return personasDir                       // 1. 主进程注入（打包场景）
  const fromEnv = process.env["PETIBI_PERSONAS_DIR"]
  if (fromEnv) return fromEnv                               // 2. 环境变量（chat 路由等无 deps 通道处）
  const url = import.meta.url
  if (!url) throw new Error("[personas] 无法推算 data/personas 目录：...")  // CJS bundle 下为空串
  ...                                                       // 3. dev / tsx / vitest 推算仓库 data/personas
}
```

注入链（与已有的 `publicDirOverride` / `postersDirOverride` 完全同构）：

```
electron/main.ts startServerInMain()
  personasDir = <dataRoot>/personas        // prod: process.resourcesPath/data/personas
  + process.env.PETIBI_PERSONAS_DIR        // 兜住 chat 路由
    ↓
server/src/embed.ts startServer({ personasDir })
    ↓
server/src/app.ts createApp({ personasDirOverride })
    ↓
server/src/routes/me.ts createMeRouter({ personasDir }) → loadPersonaCard(mbti, personasDir)
```

顺带修好的：`chat` 路由的人格层 prompt（`buildSystemPrompt` → `loadPersonaCard`）在打包版里同样读不到速查卡，会退化成通用兜底人格。`PETIBI_PERSONAS_DIR` 一并覆盖了这条路径。

兜底文案本身保留（路径真的坏掉时返回 200 + "未知/伙伴"，不 500 阻塞主链路），但现在会打 `console.warn` 带上实际目录，下次排查一眼能看出是"路径没注入"还是"文件缺失"。

## 5. 遗留与提醒

1. **`test_feedback` 是新表**：老用户的 `chat.db` 在下次启动 `ensureSchema()` 时自动建表（`CREATE TABLE IF NOT EXISTS`，幂等），无需手工迁移；已有数据不受影响。
2. **反馈的 `comment` 字段前端还没采集**：接口和表都支持了（≤200 字），UI 上目前只有「很符合/测的不准」两个按钮，后续要加"说说哪里不准"输入框时不用再动 server。
3. **`data/` 路径注入这个坑是系统性的**：`sensitive-words / intent-filter / refusals / encyclopedia` 早先都靠 env 注入绕过，personas 是漏网的最后一个。以后 server 侧任何新增 `data/*.json` 读取，必须同时在 `electron/main.ts:startServerInMain()` 加一条 env/参数注入，否则打包版必然静默走兜底。建议后续把这类路径收敛成一个 `resolveDataPath(name)` 统一入口（本次没做，避免扩大改动面）。
4. **`scripts/repro-setup-complete.mjs` 建议纳入发版前手工冒烟**：它是目前唯一能覆盖"主进程窗口生命周期"的自动化手段，vitest 层的纯函数测试挡不住这类 bug（P0-006 前两轮就是这么漏过去的）。
5. 按工单要求**未执行 git commit**；`data/`、`eval/`、`assets/`、`PRD.md`、`REVIEW.md`、`ISSUES.md`、`plan.md` 均未改动。
