## 三、契约与数据流

### 3.1 重测入口状态机（`setupStore` 角度）

```text
ProfileTab 点击「重新测试人格」
   └─ 确认弹窗 → 调 petApi.openSetupRetest()
        └─ 主进程：关 panel + 关旧 setup + createSetupWindow({ mode: 'retest', initialStep: 'pick' })
             └─ setup 窗加载 /setup/index.html?mode=retest&initialStep=pick
                  └─ EntryModeBridge：getProfile() → dispatch INIT_FROM_PROFILE
                       └─ state.mode='retest', state.step='pick', token/email/nickname 已写入
                            └─ user 在 pick 选 INTP（直接选路径）或走 test 路径
                                 └─ 结果页 → handleComplete()
                                      └─ saveProfile(server) + petApi.notifyRetestComplete({mbti, subtype})
                                           └─ 主进程：写 profile.json（保留 email/nickname/createdAt，覆盖 mbti/subtype）
                                                └─ petWin.webContents.send('pet:sprite-change', 'INTP')
                                                     └─ pet App：setMbti('intp') + setState('idle') + setFrame(0)
                                                          └─ spritePath('intp','idle',0) = 'sprites/intp/idle_0.png'
                                                              └─ 桌宠立刻换 INTP sprite（无需重启）
                                                └─ panelWin.webContents.send('panel:profile-changed')
                                                     └─ panel App：refetch getMe → 「我的」Tab 刷新
                                                └─ setupWin.close()（pet 窗已存在，不调 transitionSetupToPet）
```

### 3.2 关键契约（钉死的不可变规则）

1. **16 型白名单**：mbti 必须落在 `/^(INTJ|INTP|...|ESFP)$/i` 内，否则 `sanitizeMbti` 回退 `'intj'`。主进程在 `setup:retest-complete` 入参时也会做一次白名单校验（防御纵深）。
2. **retest 模式跳过 login/nickname**：`INIT_FROM_PROFILE` action 不走 `LOGIN_SUCCESS` / `SET_NICKNAME`，直接落 `pick` / `test`。
3. **reducer 不残留上一轮 result/answers/pickedType/feedbackRecorded**：`INIT_FROM_PROFILE` 与 `GO_PICK` / `GO_TEST` 都显式清空（P0-005 同源防御）。
4. **retest 完成不走 `completeSetup`**：`completeSetup` 会拉起新 pet 窗（与现有 pet 重复）；改走 `notifyRetestComplete` → 主进程直接关 setup 窗。
5. **retest 关闭 setup 不退出 app**：retest 模式下 `setupWin.on('closed')` 不再触发 `app.quit()`，仅清引用（用户取消重测 = 保留现有 pet 状态）。
6. **托盘 / 右键菜单结构稳定**：3 项 + 1 个 separator（M4 决策），不在后续工单里往菜单里塞功能——任何扩展走「桌宠气泡菜单」或「主面板」入口。

## 五、关键技术决策与备选

### 5.1 为什么把 sprite 路径生成抽到独立文件 `src/pet-sprite.ts`

- 原 App.tsx 是 React 组件，跑测试要么拉 DOM 环境要么写集成测试，抽离后变成纯函数，vitest node 环境直接 import，回归成本极低。
- 16 型白名单 + 兜底策略集中在一处，未来如果扩到 32 型或支持自定义人格，只需要改 `MBTI_TYPE_RE` 一个常量，路径拼接不动。
- 重构独立文件而不是新增 util 目录，避免新增空目录造成不必要的目录结构变动。

### 5.2 为什么用 `mode` 字段而不是单独的 retest reducer

- 既有 reducer 已经覆盖了 pick / test / result 的全部分支，重测流程与首次注册共用 reducer（除入口条件不同），重测的差异点只有「handleComplete 不走 completeSetup」「login/nickname 不可达」。
- 用 mode 字段扩展 reducer 既保留了既有 318 个用例不破（只在 INITIAL_SETUP_STATE 加一字段），也避免双 reducer 带来的逻辑分叉风险。

### 5.3 retest 完成后的 server 同步与本地同步

- 现状：retest 必须调 `saveProfile(token, {nickname, mbti, subtype})` 同步 server（`/api/me/profile`），不然 server 侧 user.mbti 还是旧值，下次 `getMe` 又会拉回旧人格。
- 本地 profile.json 必须保留 email/nickname/createdAt，所以不能在渲染端直接调 `petApi.setProfile`（那会覆盖 createdAt 等字段）。改由主进程读旧 profile → 仅覆盖 mbti/subtype → 写回。
- 测试也覆盖了这条路径：`setup:retest-complete` 的 16 型白名单 + profile 缺失兜底 + 写回失败时不阻塞关窗。

### 5.4 为什么右键菜单抽出 `buildPetContextMenuItems` / `buildTrayMenuItems` 纯函数

- `Menu.buildFromTemplate` 是 electron 模块方法，vitest node 环境 mock 整个 electron 麻烦且脆；抽 item 数组后，断言只需比对纯对象数组。
- 同源问题：如果未来要在菜单里加「关于 / 重启」之类的项目，两边都用同一套构造函数，不会出现「托盘有 / 右键没有」的遗漏。
